# 大模型幻觉治理

## 前置认知

**幻觉（Hallucination）**是 LLM 的固有属性，不是 bug——模型本质是概率分布上的采样器，它不知道"事实"，只知道"在训练语料里这个词出现在这个位置的概率有多高"。因此幻觉治理不是消除，而是**多道防线层层收口**，目标是让模型在不确定时宁可说"我不知道"而不是编造。

---

## 一、检索增强生成：最主流、最有效

RAG 让模型不再依赖训练记忆中的"事实"，而是先检索再回答。详见 [[RAG全链路与检索增强生成]]。

**RAG 防幻觉的核心机制**：
- 将用户问题向量化 → 从外部知识库检索相关片段 → 将问题 + 检索结果拼接为 Prompt → 要求模型**仅基于给定上下文**生成答    案
- 若检索无结果，直接让模型回答"未找到相关信息"，切断编造的可能

**关键要求**：如果 Prompt 末尾没有"请只基于以上资料回答，不要使用你的训练知识"，模型仍然可能在检索资料不足以回答时，悄悄用训练记忆补全——这正是 RAG 最常见也最隐秘的幻觉来源。真正落地的 RAG 必须在 Prompt 中显式约束这一点。

**进阶技巧（比基础 RAG 多一层验证）**：
- **Rerank 精排**：向量检索是粗筛，Rerank 模型（如 Cohere Rerank、bge-reranker）对 Top-K 逐条重打分，将最相关的 3-5 条送入 LLM。没有 Rerank 时，Top-20 里可能混入 5 条语义相似但实际无关的片段，LLM 容易被这些噪音带偏。
- **引用溯源**：要求模型在答案中标注每条事实来自检索结果的哪个片段（页码、文档名），既方便人工复核，也倒逼模型不编造。
- **Self-RAG**：模型在生成过程中自行判断"当前是否需要检索"和"刚生成的句子是否和检索事实一致"，把检索决策内化到生成循环中，而不是仅在开头查一次。

**与幻觉治理的边界**：RAG 管的是"模型不知道的事"——训练截止日期之后的新信息、企业私域数据。如果模型训练时已经见过但记错了（如历史日期张冠李戴），RAG 也能纠正，前提是正确资料被检索到了。

## 二、控制采样与解码策略

模型的"创造性"来自随机采样，减少随机性可直接降低幻觉。详见 [[模型推理与运行时优化]]。

### 2.1 采样参数控制

| 参数 | 防幻觉设置 | 原理 |
|------|-----------|------|
| `temperature` | 0.1~0.3 | 降低 logits 分布的熵，使模型倾向选最高概率的 Token |
| `top_p` | 0.7~0.85 | 只从累积概率达到 p% 的 Token 中采样，砍掉长尾 |
| `top_k` | 20~40 | 只从概率最高的 k 个 Token 中选 |
| `repetition_penalty` | 1.05~1.15 | 惩罚已出现过的 Token，防止陷入重复循环（重复≠幻觉，但重复时模型往往已经"放弃思考"） |

> **注意**：temperature 和 top_p 不建议同时往极端了调。temperature 已经在压低分布熵，再用很低的 top_p 会让候选 Token 只剩 2-3 个，输出变得机械重复，反而触发另一种"退化"。

### 2.2 关键场景使用 Greedy Decoding

在事实性要求极高的环节（翻译专有名词、数学计算、代码补全），关闭采样，使用贪心解码（每次选概率最大的 Token）。`do_sample=False` 或 `temperature=0`。

代价是输出多样性消失——所以只在需要精确性的片段使用，而非整段对话。

### 2.3 约束解码

比修改采样参数更"硬"的防幻觉手段：在输出层面直接限制模型只能说特定格式/特定词汇。

| 工具 | 方式 | 适用场景 |
|------|------|---------|
| `guidance` | 模板语法交错的约束生成 | JSON 输出、对话格式控制 |
| `outlines` | 用正则或 CFG 文法约束 | 代码生成、结构化字段 |
| `lm-format-enforcer` | JSON Schema 约束 | API 响应格式化 |

**防幻觉机制**：如果你要求模型输出 `{"city": "北京"}`，但模型想输出 `{"city": "北京是中国的"}`，约束解码会在 `是` 这个 Token 被采样前直接把它从候选列表中删掉——模型根本没有机会输出它。

### 2.4 Logits 层面的干预

除了修改采样参数，还可以直接在 logits 上操作：
- **Logit Bias**：给特定 Token（如"可能""也许"）增加概率偏移，引导模型倾向不确定性表达
- **Ban Tokens**：直接禁止某些 Token 出现（如禁止绝对化表达"必然""100%"）

## 三、后处理验证与自我纠错

让模型在某些关键维度上"检查自己"。

### 3.1 链式验证

来自 2023 年 Chain-of-Verification 论文的四步法：

1. 模型生成初步回答
2. 模型针对回答中的每个事实点，生成一个验证问题（问得越具体越好，如"X 事件发生在 Y 年吗？"而不是"我答对了吗？"）
3. 重新检索或再次调用模型回答这些验证问题
4. 对比初始回答与验证结果，修正不一致处

**实施要点**：第 2 步是决定验证质量的关键——如果验证问题太笼统，模型大概率会"确认"自己的幻觉（自己骗自己）。验证问题必须拆到原子事实粒度。

### 3.2 分解验证

```text
原始问题："2023 年特斯拉 Q3 营收与交付数据"

分解：
1. "2023 年特斯拉 Q3 总营收是多少？"
2. "2023 年特斯拉 Q3 汽车交付量是多少？"
3. "以上两个数据出自哪份财报？"

逐个回答 → 交叉比对 → 检查来源一致性
```

当子问题答案之间出现矛盾（如 Q1 说营收同比增长 9%，Q3 的来源指向另一份报告），就是高置信度的幻觉信号。

### 3.3 外部一致性检查

将答案中的事实拆成 (主体, 关系, 客体) 三元组，与知识图谱或数据库比对。适用于企业场景中已有结构化知识库的情况。

### 3.4 LLM-as-Judge

用一个独立的、更强的模型做裁判。实践中常用：
- **同模型自评**：成本低但可能有盲区（模型不太会发现自己的错误）
- **更强模型评审**：用 Claude/GPT-4 评审弱模型的输出，效果好但成本高
- **交叉评审**：两个不同家族的模型互相评审，减少家族偏见

## 四、反馈学习与微调

从训练层面减少幻觉倾向。详见 [[大模型微调与参数高效化]]。

### 4.1 RLHF

在强化学习阶段设计专门的奖励信号：
- 模型回答"我不知道"而非编造 → 正奖励
- 模型生成本应能检索但未检索到的事实性错误 → 负奖励
- 引用外部知识并标注来源 → 正奖励

**实施难点**：事实性错误的判断成本很高——需要人工标注或可信的外部数据源做自动判断，否则奖励信号本身可能就是错的。

### 4.2 DPO：比 RLHF 更轻量的替代

DPO 不需要单独训练奖励模型。直接构造偏好对：
- 优选回答：引用来源、不确定时承认、拒绝编造
- 劣选回答：编造事实、掩盖不确定性

模型直接学习"真实回答优于幻觉回答"的偏好。实践中 DPO 对事实性的改善不如 RLHF 精细，但数据准备和训练成本低一个数量级。

### 4.3 事实性数据集

| 数据集 | 用途 | 特点 |
|--------|------|------|
| TruthfulQA | 评估事实性 | 覆盖 38 个类别的人类常见误解 |
| HaluEval | 幻觉检测 | 包含幻觉答案和对应真实答案 |
| FELM | 事实性评估 | 覆盖多个领域的事实性基准 |

## 五、工具调用

让模型调用工具获取真实数据，而非凭训练记忆创作。详见 [[AI Agent架构与并发控制流]]。

### 5.1 基本原则

凡是涉及以下场景，不允许模型直接输出结论，必须走工具调用：
- **数学计算**：让模型写 Python 代码执行，而非口算
- **实时数据**：天气、股价、新闻 → 调 API
- **精确日期**："下周二"、"两个月后" → 用日期计算函数
- **数据库查询**：不要让模型"猜"数据库里有什么

### 5.2 Function Calling 标准模式

```python
# 模型输出函数调用参数，代码执行函数，结果返回模型
response = model.generate(
    messages=[...],
    tools=[{
        "name": "get_current_temperature",
        "description": "获取指定城市的当前气温",
        "parameters": {"city": "string"}
    }]
)
# 模型返回 {"name": "get_current_temperature", "parameters": {"city": "北京"}}
# 代码执行函数获取真实温度 32°C
# 将 32°C 作为 tool_result 再次传入模型
# 模型基于真实数据生成回答
```

**防幻觉关键**：函数执行结果必须原样传回模型 Context，不做截断、不改写。任何中间处理都可能引入新的信息失真。

### 5.3 结构化输出与校验

要求模型输出 JSON Schema 或 Pydantic 模型定义的格式，并在代码层加入校验逻辑：
- 日期字段："开始日期 < 结束日期"
- 数值范围："概率值在 0-1 之间"
- 枚举约束："状态只能是 pending/approved/rejected"

校验失败时，将错误信息传回模型让其修正，形成"生成 → 校验 → 修正"循环。

## 六、不确定性表达与拒答

### 6.1 语言层面的约束

**禁止使用的表达**：总是、从未、毫无疑问、100%、所有专家一致认为、绝对

**鼓励使用的表达**：根据现有信息、可能是、有证据表明、截至 XX 日期、目前尚无定论

这不仅仅是措辞优雅——当模型使用绝对化表达时，它自己也会"相信"这个表达，进而围绕它展开更多编造（一个谎言需要十个谎言支撑）。鼓励不确定性表达实质上是打断幻觉的自我强化链条。

### 6.2 置信度与拒答

**输出置信度**：让模型在回答末尾附加置信度（如 `[置信度: 85%]`），并设定阈值——低于阈值的回答标记"需人工确认"或直接拒答。

**注意**：未经专门校准的模型，其自评置信度往往不准（过于自信或过于保守都不利于使用）。生产环境需要：
- 在验证集上做置信度校准（使置信度与实际正确率匹配）
- 计算 Expected Calibration Error (ECE) 衡量校准质量

### 6.3 Logit 分布的拒答信号

当模型在生成关键 Token 时，若 top-1 和 top-2 Token 的 logit 值差距很小（如差值 < 0.3），说明模型对两个答案几乎同样"犹豫"，此时强行选一个极大概率是在编造。可以设定 logit-gap 阈值，低于阈值时触发拒答。

## 七、任务分解与最小单元承诺

**核心思想**：一个复杂问题的幻觉概率是各个子环节的乘积。把问题拆成相互独立的原子单元，可以阻止幻觉在不同子问题之间"传染"。

### 7.1 原子问题拆分

```text
复杂问题："分析中国 2023-2025 年新能源汽车出口趋势"

拆分为独立子问题：
1. 2023 年中国新能源汽车出口量
2. 2024 年中国新能源汽车出口量
3. 2025 年 Q1 中国新能源汽车出口量
4. 主要出口目的地国家 Top-5
5. 同比增长率计算

→ 分别回答 → 各自验证 → 最后组合
```

### 7.2 逐步承诺

模型每生成一个中间结论，先确认该结论是否与已知事实或检索结果矛盾，再继续下一步。相当于在推理链上每隔几步设一个检查点，防止推理链条某一步的幻觉导致后续全部偏离。

**与 Chain-of-Thought 的区别**：CoT 让模型"展示推理过程"，但不验证推理是否正确。逐步承诺在每一步都加入事实核对环节，把 CoT 从"想"升级为"想一步、查一步"。

## 综合建议

优先级从易到难排列：

| 优先级 | 方法 | 实施成本 | 收益 |
|--------|------|---------|------|
| **立即见效** | 降低 temperature + 接入 RAG + 约束 Prompt 要求引用来源 | 低 | 高 |
| **低成本改进** | Chain-of-Verification 后处理自检 + 结构化输出校验 | 中 | 中高 |
| **产品级稳定** | 约束解码 + 工具调用替代模型推理 | 中高 | 高 |
| **长期投入** | DPO/RLHF 基于事实性奖励的微调 | 高 | 根本性改善 |

**最后一条防线**：没有模型能保证 100% 不产生幻觉。在关键业务场景中，低置信度输出应自动标记"需人工确认"，并设计人工复核流程——这不是技术能力的退步，而是对 LLM 本质的正确认知。

## 落地应用

1. **这个知识是为了解决什么问题**：LLM 的输出不可信——它会用非常自信的语气说出完全错误的事实。幻觉治理是一套多道防线的工程方案，让模型在不确定时宁可不回答，而不是编造。
2. **真实开发里会出现在哪**：AI 客服（瞎编退换货政策会引发客诉）、医疗问诊（幻觉可能危及生命）、金融分析（捏造数据会导致错误决策）、企业内部知识问答（编造流程会耽误业务）。任何"模型输出会被用户直接使用"的场景都需要幻觉治理。
3. **一个最小实践 Demo**：
```python
import openai

def ask_with_rag_and_verification(question, knowledge_base):
    # Layer 1: RAG — 先检索再回答
    retrieved = knowledge_base.search(question, top_k=5)
    context = "\n".join([f"[来源{r['id']}] {r['content']}" for r in retrieved])
    
    prompt = f"""请仅基于以下资料回答问题。如果资料不足以回答，请说"根据现有资料无法确定"。
资料：{context}
问题：{question}
回答（必须标注来源编号）："""

    answer = openai.chat.completions.create(
        model="gpt-4", messages=[{"role": "user", "content": prompt}],
        temperature=0.2  # Layer 2: 低温度减少随机性
    )
    
    # Layer 3: 简单自检 — 答案中的事实是否在检索片段中出现？
    for r in retrieved:
        if r['id'] in answer and r['content'] not in answer:
            return f"[需人工确认] {answer}"
    
    return answer
```
4. **一个真实项目中的使用场景**：某企业内部知识问答系统——接入了公司 Wiki + 工单系统作为知识库。用户问"这个版本什么时候发版"时，RAG 检索到最新发版计划文档，模型基于文档回答，并引用发布日期来源。若检索不到相关文档，模型回复"暂未找到该版本的发版计划，建议联系 PM"。同时，回答末尾标注置信度，低置信度的回答自动转人工客服。
5. **初学者最容易犯的错误**：（1）只调 Prompt 不做 RAG，以为精细的 Prompt 就能治好幻觉——Prompt 只能约束模型"怎么说"，不能给模型"不知道的知识"；（2）RAG 查到了但模型没用——因为没有在 Prompt 末尾显式要求"只基于以上资料"；（3）temperature=0 就让所有业务场景都用——零温度在对话中会让输出机械单一，只在事实性校验环节局部使用。
6. **当前阶段只需要掌握到什么程度**：能说清七种防幻觉方法的核心原理、适用场景和局限性；能搭建一个"RAG + 低温度 + 引用来源提示"的最小幻觉治理方案；知道什么情况下幻觉还是会出现，并能向他人解释"为什么 LLM 不可能 100% 不产生幻觉"。
7. **学完后建议做什么练习**：用 LangChain 或原生 API 搭建一个带幻觉治理的问答 Demo：先不加任何限制让模型回答一个它不可能知道的问题，观察幻觉产生；然后依次加上 RAG、降低温度、要求引用来源，对比同一个问题的回答质量变化。
