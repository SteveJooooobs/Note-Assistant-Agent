# ILU 项目 Agent 架构映射笔记 (Project-to-Agent Architecture Mapping)

将已完成的 ILU 智能家居 NLU 系统拆解到 Agent 统一认知框架中，识别已有 Agent 特征、可升级模块与不可交由 LLM 的安全边界。

---

## 1. ILU 模块 → Agent 架构完整映射

### 概念详解
ILU 的完整链路：用户输入 → 意图分类 → 槽位填充 → 规则编排 → 追问状态机（条件触发）→ 策略引擎拦截 → 设备管理器执行 → 输出。将这条链路映射到 Agent 的统一认知框架：

| ILU 模块 | Agent 架构位置 | 对应抽象 | 是否可被模型替代 |
|----------|---------------|---------|-----------------|
| 意图分类模型 | Planner 第一跳 | 意图路由——判断"控制/查询/闲聊" | 🟢 已是模型（MacBERT） |
| 槽位填充 | Planner 第二跳 / Function Calling | 结构化输出——提取("设备=空调","动作=开")并下发给 Tool | 🟢 已是模型，当前用 MacBERT 实现 |
| 规则编排器 | Planner → Tool 之间 | 多任务切割、隐式意图拆分——Planner 的规则版 | 🟡 可被模型替代，但规则版更可控 |
| 追问状态机 | Planner ↔ Tool 循环边 | 信息不完整时触发二次交互，携带一次会话内的记忆 | 🟡 模块可用 LangGraph 条件边升级 |
| 策略引擎 | Tool → Output 之间的拦截层 | 数据合法性校验、物理安全规则、风险分级 | 🔴 永远不该交给 LLM |
| 设备管理器 | Tool 层 | 接收拼装好的 JSON，拆参数、读写设备状态 | 🟢 已是 Tool |
| JSON 指令组装器 | Tool ↔ 设备管理器之间 | 将意图+槽位转译成设备可理解的指令格式 | 🟢 已是 Tool |

### 知识点关联
- **与 LangGraph 的对应**：ILU 的追问状态机是一个只有 4 个 Node、3 条条件边的最简 LangGraph。当时用 if-else 实现，现在回头看——Node（意图分类/槽位填充/追问/拼装指令）、条件边（槽位完整→拼装；缺失→追问）、State（意图+槽位字典+缺失字段列表）——三项要素全部具备，只是没管它叫 LangGraph。
- **Function Calling 就是 Planner → Tool 之间的那根箭头**：它不是一个独立组件。槽位填充模型输出的结构化 JSON（意图标签+槽位键值对）本质上就是一次 Function Calling——模型输出"意图+参数"，代码负责执行。区别仅在于 ILU 用 MacBERT 而非 LLM 做这一步。
- **追问状态机的两派做法**：程序派（硬编码字段完整性检查，确定性 100% 但场景依赖代码）vs LLM 派（让 LLM 判断信息够不够，灵活但边界模糊）。ILU 选择程序派是正确的——设备控制的参数缺失定义是精确的（温度必须是一个数值），不需要 LLM 来猜。

### 工业级应用举例
如果在 ILU 之上扩展为生产级智能家居 Agent：意图分类和槽位填充合并为一个 LLM Function Calling 调用（一次性输出 `{intent: "control", function: "set_ac", params: {temp: 26}}`），追问逻辑改用 LangGraph 条件边（if 参数不完整 → 追问 Node；else → 执行 Node），策略引擎保持纯代码拦截不变。

## 2. MCP 与 JSON 组装器：下行与上行标准化

### 概念详解
ILU 的 JSON 指令组装器做的是**下行标准化**——Agent 的意图被转译成设备能理解的格式：

```text
意图+槽位 → JSON组装器 → {"action":"on", "device":"AC", "temp":26} → 设备管理器
```

MCP（Model Context Protocol）做的是**上行标准化**——Tool 的能力被描述成 LLM 能理解的格式：

```text
Tool能力+参数Schema → MCP协议 → LLM发现并理解该Tool
```

两者不是"前身与后继"的关系，而是**同一枚硬币的两面**：下行让下游理解上游，上行让上游发现下游。合在一起就是 Agent 与 Tool 之间的完整通信协议层。

### 知识点关联
- **与 USB 协议的类比**：MCP 就是 USB 标准。USB 让电脑能自动识别任何符合标准的键盘/U盘/鼠标，MCP 让 LLM 能自动发现任何符合标准的 Tool。没有 USB，每换一个外设就要重装驱动；没有 MCP，每加一个 Tool 就要手写适配代码。
- **为什么 ILU 不需要 MCP**：ILU 只有 3~5 个 Tool（设备开/关/查询/定时），手写适配代码的成本可以忽略。当 Tool 数量从 5 个变成 100 个时，MCP 从"可有可无"变成"没有就活不下去"。

### 工业级应用举例
面试场景中，如果有人问"你理解 MCP 吗"：可以直接用 ILU 项目的 JSON 组装器做对比——"我在项目里解决的是下行问题（让设备理解 Agent），MCP 解决的是上行问题（让 Agent 发现工具）。两者合在一起才是完整的 Agent-Tool 通信层。"

## 3. 计算图中的"静态"与"动态"：PyTorch vs LangGraph

### 概念详解
"动/静"需要从两个维度拆开看：

**维度一：图何时被构造？**
- PyTorch：每次 forward 即时构建（define-by-run），backward 后销毁。如果 forward 中有 if-else，不同输入可能走出不同的图结构。属于**动态计算图**。
- LangGraph：Node 和 Edge 在编译时注册完成，不走不建。属于**静态注册**。

**维度二：路由决策能否运行时改变？**
- PyTorch：模块连接关系在 `__init__` 中固定，forward 中的 if-else 只能在已存在的分支中二选一。路由逻辑嵌入代码，不可视化。
- LangGraph：条件边的目标由运行时 State 决定，路由逻辑从代码提升到图拓扑层面，显式、可追踪、可审计。

### 知识点关联
一句话总结：**LangGraph 提供地图，导航去哪由实时状态决定；PyTorch 按实际执行路径动态构建图，目的是反向传播能原路返回。** 一个服务于"人理解系统"，一个服务于"机器计算梯度"。

### 工业级应用举例
在 Agent 的运维场景中，当某次对话走了一条异常的"意图→三次追问→超时→Fallback"路线，LangGraph 的显式图拓扑让运营团队可以直接看到路由轨迹。PyTorch 的图是为了 autograd 设计的，不具备这种审计能力。两者的"图"虽然同名，但服务对象完全不同。

## 4. Agent 的统一认知定位

### 概念详解
ILU 的完整流程（不含外部的用户输入和下游的执行硬件）已经构成一个 Agent。与标准 Agent 的差距在于：
- 模型不直接调用 Tool——当前是"模型输出 → 规则编排 → Tool"，而非"模型决定 → Tool 执行"
- Memory 不完善——追问状态机只有一次会话内的临时记忆，没有会话间的长期记忆

但骨架已经完全一致：感知（意图+槽位）→ 规划（规则编排+追问决策）→ 执行（设备管理）→ 反馈（追问/结果），这正是 Agent 循环的原始形态。

### 知识点关联
- **从传统 NLU 到 Agent 的进化路径**：ILU → 把规则编排换成 LLM → 加上 Function Calling 让 LLM 直调 Tool → 加上 MCP 让 Tool 自描述 → 加上 LangGraph 管理复杂分支 → 加上 Memory 实现跨会话记忆 → 完整 Agent。这不是推翻重来，是**渐进升级**。
- **Agent ≠ LLM + Tool**：ILU 用 MacBERT 而非 LLM，但它仍然是 Agent 架构。Agent 的核心是"感知→规划→执行→反馈"的循环模式，不是"用了哪个模型"。框架只是实现手段。
