# RAG 全链路与检索增强生成 (Retrieval-Augmented Generation Full Pipeline)

RAG（检索增强生成）为 LLM 提供了一套可实时更新的外部知识库，模型无需重新训练即可获取最新知识。它由八个环节串联而成，每层都有明确的工程取舍。

---

## 1. 全链路总览

### 概念详解
RAG 的完整数据流：

```text
文档 → 切块 → Embedding → 向量库 → 检索(召回) → Rerank → 拼接Prompt → LLM生成
```

其中切块到向量库属于**离线索引阶段（Ingestion Pipeline）**，检索到生成为**在线查询阶段（Query Pipeline）**。两阶段分离是 RAG 系统可扩展的前提——索引慢但只需做一次，查询快但每次对话都要走一遍。

### 知识点关联
- **RAG 三字拆解**：检索（Retrieval）为模型提供知识查询能力；增强（Augmented）将模型已有知识与检索到的最新知识拼接输出；生成（Generation）将拼接后的完整 Prompt 交给 LLM 做最终输出。面试时用三字拆解法解释 RAG，比背定义更自然。
- **RAG 的不可替代价值**：不是"让 LLM 回答得更准"，而是"让 LLM 知道它不知道的事"。模型训练有截止日期，RAG 绕过重新训练的巨额成本，通过外部知识库实现实时更新。

### 工业级应用举例
企业内工单查询系统：每日新增工单实时写入向量库，客服 Agent 查询时先检索相关工单再生成回复。没有 RAG，每新增一个工单就需要重新微调模型——时间和成本都不现实。

## 2. 文档切块：检索质量的第一道关卡

### 概念详解
长文档在 Embedding 前必须切分为语义完整的块。切块策略直接影响检索精度：

| 策略 | 做法 | 适用场景 |
|------|------|---------|
| 固定大小切 | 按 token 数等分，如每 512 token 一块 | 通用场景，简单但可能切断语义 |
| 按段落切 | 以自然段为边界 | 结构化文档（Markdown、网页） |
| 按主题切 | 基于标题或语义聚类 | 层级清晰的文档，如技术手册 |
| 父子块 | 父级存段落主旨，子级存具体内容 | 语义检索精度要求高的场景 |

所有策略都需预留**滑动窗口**（通常 10%-20% 重叠），避免上下文在块边界被切断。文档预处理也很关键：Word 去格式和水印、PDF 处理 OCR、网页提取正文——数据清洗不到位，后续所有环节都在垃圾上工作。

### 知识点关联
- **与 Transformer QKV 的类比（理解检索本质）**：模型携带 Query（用户问题），检索时在向量库中匹配最相似的 Key（块描述/向量），找到 Top-K 后取出对应的 Value（实际文档块）。这个类比揭示了 RAG 检索与 Attention 机制的深层一致性——两者都在做"用 Q 去找最相关的 V"。**这也是为什么很多 RAG 优化方向（多向量检索、ColBERT 晚交互）的本质都是在"把 KV 怎么存、怎么查"上做文章。**
- **父子块就是 KV 的一种工程实现**：父级块（K）存段落主旨用于匹配，子级块（V）存具体内容作为返回给 LLM 的上下文。比固定大小切块多了一层抽象，检索精度更高。

### 工业级应用举例
金融研报 RAG：一份 50 页的 PDF 研报如果按固定 token 数切块，可能把"2024 年 Q3 营收同比增长 15%，主要由云计算业务驱动"切成两块，丢失因果关系。按段落切+10%滑动窗口能保持语义完整。同时研报中的表格需要 OCR 提取、页眉页脚的免责声明需要过滤——这些"脏活"决定了 80% 的检索质量。

## 3. 检索策略：稀疏、稠密与混合

### 概念详解
检索层决定了"用什么方式找到最相关的文档块"，有三种主流策略：

- **稀疏检索（Sparse Retrieval）**：基于关键词匹配，如 BM25、TF-IDF。适合精确匹配（产品名、型号、ID），但无法理解同义词（"省电模式"和"节能方案"匹配不到）。
- **稠密检索（Dense Retrieval）**：将查询和文档都映射为语义向量，计算余弦相似度。能处理语义搜索（"我有点热"→联想空调/风扇），但可能丢失精确关键词匹配。
- **混合检索（Hybrid Retrieval）**：稀疏+稠密加权融合，生产环境主流。兼顾精确匹配的高召回和语义搜索的高覆盖率。

### 知识点关联
- **与 ILU 项目的对应**：ILU 中用户说"打开客厅空调"，这是精确匹配——设备名"空调"和位置"客厅"都是确定值，稀疏检索就够用（甚至 BM25 都不需要，直接精确查数据库）。但如果用户说"我有点热"，就变成了语义搜索，需要 Embedding 去联想"热→降温→空调/风扇"。**生产环境的智能家居 Agent 必须同时支持两种——因为用户两种都会说。**

### 工业级应用举例
电商客服 RAG：用户搜索"iPhone 充电器"用稀疏检索精确匹配产品名；用户问"手机没电了怎么办"用稠密检索理解语义。混合检索对两条结果列表做加权融合（如 BM25 权重 0.3 + 向量相似度权重 0.7），取交集或并集中的 Top-K 作为最终召回结果。

## 4. Rerank：从粗筛到精排

### 概念详解
向量检索是粗筛——速度快但精度有限，Top-K 中可能混入语义相似但实际无关的结果。Rerank 是精排——用一个更强的模型（通常是 Cross-Encoder）对粗筛得到的 Top-K 逐条打分，重新排序，最终只保留最相关的 3-5 条送给 LLM。

两级流水线：粗筛（召回 100 条）→ 精排（保留 5 条）→ LLM。平衡了速度和精度。

### 知识点关联
- **为什么需要 Rerank**：向量检索用的是双塔模型（Query 和 Document 分别编码后算相似度），速度快但交互只在最后一层；Cross-Encoder 将 Query 和 Document 拼接后一起输入，交互发生在每一层，精度高但速度慢。**Rerank 的核心思想是：用快模型缩小范围，用慢模型精细筛选。** 这种"粗筛-精排"模式在搜索引擎中已经用了二十年，RAG 借用了同一思路。

### 工业级应用举例
法律文档 RAG：用户问"竞业限制的有效期"，向量检索可能召回大量包含"竞业""限制"但实际上是关于竞业补偿金而非有效期的文档。Rerank 用更强的模型重新判断每一条与问题"竞业限制的有效期"的实际相关性，将真正相关的 3 条排在前面。如果没有 Rerank，LLM 可能在 20 条噪音中生成错误的答案。

## 5. RAG 的瓶颈

### 概念详解
RAG 的瓶颈不在模型，而在数据管道的质量。具体落在三个环节：

1. **数据清洗质量**：文档中的噪声（水印、页眉页脚、格式乱码）未经清洗直接 Embedding，检索时噪音也会被匹配到。
2. **切块策略不当**：切太碎丢上下文，切太大检索精度降。没有一种策略适合所有文档类型。
3. **检索-生成脱节**：检索召回了正确内容，但 LLM 没有正确使用（忽略、曲解、或过度信任检索结果）。

三点合起来一句话：**RAG 的瓶颈高度依赖于其内容质量。** 垃圾进，垃圾出。

### 知识点关联
- **与 ILU 数据处理经验的关联**：ILU 的数据生成阶段做的标注清洗、格式校验、BIO 标签对齐——这些工作本质就是 RAG 数据管道的雏形。你做过的"清洗训练数据"和 RAG 的"清洗索引数据"，工序完全相同，只是目标不同。

### 工业级应用举例
医疗 RAG 中，如果药品说明书在切块时把"禁忌症"和"适用症"切到了同一块，检索出这块后 LLM 可能混淆两者，给出危险的回答。这是切块策略导致的生命安全问题，而非模型问题。

## 6. RAG 的适用边界

### 概念详解

**需要 RAG 的场景**：信息实时变化或有明确的知识截止需求。如企业工单系统、员工差旅助手、金融市场每日动向、产品文档实时更新。

**不需要 RAG 的场景**：依赖稳定已有知识的，如图书管理系统、历史知识检索、非前沿数理化概念等；或有明确工具调用的场景，直接走 Function Calling 更高效。

### 知识点关联
- **何时用 RAG，何时用微调**：RAG 适合"知识更新快"的场景（每天新的工单、新闻、产品文档——更新向量库即可）。微调适合"行为模式稳定"的场景（让模型学会用某种风格回答、遵循某种推理模式——更新模型权重）。两者不是替代关系，而是**RAG 管"知道什么"，微调管"怎么表达"**。面试被问到"RAG vs 微调"，这个回答框架比列举优缺点更强。

## 7. 与 ILU 项目的映射

### 概念详解
ILU 中已有 RAG 的雏形，在以下位置可以直接映射：

| ILU 已有能力 | RAG 对应环节 | 说明 |
|-------------|-------------|------|
| 数据生成阶段的清洗（去重、格式校验） | 数据预处理（Ingestion Pipeline） | 工序相同，目标不同 |
| 设备知识库（设备名→设备ID→设备能力映射） | 向量库 + 检索 | 当前是精确匹配查表，可升级为语义检索 |
| 模型查设备是否存在再决定如何回应 | Tool-use RAG | 不是把知识塞进 Prompt，而是模型主动调 Tool 查 |

### 知识点关联
- **从精确查表到语义检索的升级路径**：当前 ILU 的"设备知识库"是 key-value 精确匹配（"空调"→设备 ID→属性）。如果设备从 5 个扩展到 500 个，用户可能说"那个挂在卧室墙上的东西"而不是"卧室空调"，精确匹配就失效了。这时需要 RAG 的语义检索——把设备描述 Embedding 后存入向量库，按语义相似度匹配。
- **Tool-use RAG vs Naive RAG**：Naive RAG 先把知识塞进 Prompt 再让 LLM 回答，简单但每次对话都消耗大量 Token（即使不需要那些知识）。Tool-use RAG 让 LLM 主动决定何时查 RAG，更省 Token、更可控。ILU 的"查设备→回应"流程已经是 Tool-use RAG 的前身。
