# 分词器特殊标记与主流算法

## 一、特殊标记速查

特殊标记是分词器预留在词表中的固定 ID，不参与语义计算，仅用于控制序列边界和异常处理。

| 标记 | 全称 | 作用 | 出现位置 |
|------|------|------|----------|
| `[BOS]` / `<s>` / `<bos>` | Beginning of Sequence | 标记序列起始 | 句首 |
| `[EOS]` / `</s>` / `<eos>` / `[SEP]` | End of Sequence / Separator | 标记序列结束 / 分隔两个句子 | 句尾 / 两句之间 |
| `[UNK]` / `<unk>` | Unknown | 代指词表中不存在的词 | 遇到 OOV（未登录词）时 |
| `[PAD]` / `<pad>` | Padding | 将不等长序列补齐到统一长度 | 短序列末尾填充 |
| `[MASK]` / `<mask>` | Mask | 遮盖需要模型预测的词 | BERT 预训练中被遮住的词位置 |
| `[CLS]` | Classification | 聚合整句信息，用于分类任务 | BERT 句首 |

### 1.1 BOS 与 EOS —— 边界标记

**为什么需要它们？**

自回归模型（GPT 系）逐 Token 生成文本时需要知道"何时开始、何时停止"：

- **BOS**：告诉模型"一个新句子开始了"，作为第一个 Token 输入，让模型基于它生成第一个真正有意义的词。
- **EOS**：模型输出 EOS 时意味着"这句话说完了"，解码器停止生成。如果没有 EOS，模型会无限生成直到达到 max_length。

**不同框架的命名差异：**

| 框架 | BOS | EOS |
|------|-----|-----|
| GPT-2/3/4 Tokenizer | `<\|endoftext\|>`（BOS 和 EOS 共用） | 同上 |
| LLaMA | `<s>` | `</s>` |
| BERT | `[CLS]`（兼任） | `[SEP]`（兼任） |
| T5 | —（不使用 BOS） | `</s>` |
| SentencePiece | `<s>` | `</s>` |

> **关键认知**：GPT 系列把 BOS 和 EOS 合并为同一个标记 `<|endoftext|>`——文档之间用它分隔，句首句尾也是它。本质上它在说"一段文本的边界"。

### 1.2 UNK —— 未登录词标记

**为什么需要它？**

词表不可能覆盖所有词汇。当分词器遇到一个完全无法拆分的字符时（如罕见 Unicode 字符、乱码），需要一个兜底标记。

**不同策略对 UNK 的态度：**

| 策略 | 对 UNK 的态度 | 说明 |
|------|--------------|------|
| 词级分词（Word-Level） | 严重依赖 UNK | 不在词表的词全部映射为 UNK，信息大量丢失 |
| 字符级分词（Char-Level） | 几乎不需要 UNK | 所有字符都在词表里，不存在的概率极低 |
| 子词分词（BPE / WordPiece） | 极少使用 UNK | 通过逐级拆分最终总能落到单个字符，UNK 仅作为最后兜底 |
| SentencePiece | 默认不用 UNK | 把所有输入视为纯字符序列，用 `<unk>` 的 ID=0 作为 fallback |

> **核心认知**：现代 LLM 几乎看不到 UNK 输出，因为 BPE/SentencePiece 会把陌生词一路拆到单个 Unicode 字节，除非输入本身就是损坏的。

### 1.3 PAD —— 填充标记

**为什么需要它？**

GPU 并行计算要求 batch 中的所有序列长度一致。PAD 负责把短序列"垫长"。

```
batch 中有 3 个句子：
  [BOS] 我  喜欢 机器 学习 [EOS]            → 长度 6
  [BOS] 你  好    [EOS]                     → 长度 4
  [BOS] Transformer 很  强大  真的 [EOS]     → 长度 6

补齐后（pad_token_id = 0）：
  [BOS] 我     喜欢    机器    学习    [EOS]        → 长度 6
  [BOS] 你     好      [EOS]   [PAD]   [PAD]       → 长度 6
  [BOS] Trans   很      强大    真的    [EOS]       → 长度 6
```

**PAD 必须配合 Attention Mask**：在自注意力计算中，PAD 位置的 attention 权重会被设为负无穷（softmax 后趋近 0），确保 PAD 不参与语义交互。

### 1.3.1 双重保障机制：Attention Mask 与 Loss Mask (ignore_index = -100)

在包含特殊标记或填充标记的序列任务（如命名实体识别、槽位填充）的训练中，通常会使用两层“掩码”机制来确保模型正常学习：

| 机制 | 发生阶段 | 作用目标 | 具体实现 | 核心目的 |
|---|---|---|---|---|
| **Attention Mask** | 前向传播 (Forward) | 注意力权重 (Attention Weights) | 自注意力计算中将 `[PAD]` 权重设为 $-\infty$，使其 softmax 后趋近于 0 | 防止模型在编码时受到 `[PAD]` 这种无意义 Token 的语义干扰（即**不参与注意力分配的计算**） |
| **Loss Mask (`ignore_index = -100`)** | 损失计算 (Loss/Backward) | 梯度更新 (Gradient Updates) | 损失函数底层通过条件判断 `if (target[i] == -100)` 跳过该 Token 的损失计算（将其 loss 设为 0） | 防止 `[CLS]`、`[SEP]` 或 `[PAD]` 等无语义位置的预测误差产生梯度，从而**避免污染模型的权重更新** |

**PyTorch 中 `-100` 的底层原理：**
- 它并不是通过某种数学公式计算出 0，而是底层 C++/CUDA 代码中的一个 **条件过滤逻辑（if-branch）**。
- 当样本的真实标签（target）为 `-100` 时，损失函数直接将其对应的 Loss 强制设为 `0`，并调整分母（通常是求平均时的 Token 数）。
- 因为 $Loss[i] = 0$，其对模型参数的偏导数（梯度）也恒为 `0`。在反向传播时，误差信号不会从这些位置传回，从而实现了屏蔽。

### 1.4 MASK —— 掩码标记（BERT 独有）

**仅 BERT 族模型使用。** 预训练时随机遮盖 15% 的 Token，让模型根据上下文"填空"。被盖住的词替换为 `[MASK]`。

```
输入：  我 喜欢 机器学习
遮盖后： 我 [MASK] [MASK] 学习
目标：  模型预测这两个 [MASK] 分别是 "喜欢" 和 "机器"
```

GPT 族（自回归）不使用 MASK，因为训练方式是从左到右预测下一个词，不需要遮盖。

### 1.5 CLS —— 分类聚合标记（BERT 独有）

**仅 BERT 族模型使用。** 放在每个输入序列的最前面，经过所有 Transformer 层后，该位置的输出向量被认为聚合了整个句子的语义信息，直接接一个分类头做句子级任务（情感分类、文本匹配等）。

GPT 族不需要 CLS，因为自回归模型通过最后一个 Token 的输出做预测。

## 二、两类模型的特权标记对比

| 特性 | GPT 族（自回归） | BERT 族（自编码） |
|------|-----------------|-------------------|
| 核心标记 | BOS/EOS（常合并） | CLS + SEP + MASK |
| PAD | 有 | 有 |
| 生成时停在哪 | 输出 EOS | 不生成文本，做分类填空 |
| 训练方式 | 从左到右预测下一个 Token | 双向上下文填空 |

## 三、主流分词算法一句话对比

| 算法 | 代表模型 | 核心思路 | 典型词表大小 |
|------|---------|---------|-------------|
| **BPE**（Byte Pair Encoding） | GPT-2/3/4, LLaMA, RoBERTa | 从字符开始，统计最高频的相邻符号对，反复合并 | 50K~100K |
| **WordPiece** | BERT | 类似 BPE，但合并依据不是频次而是"互信息最大化"（选能让训练语料似然提升最大的那对） | 30K |
| **SentencePiece** | LLaMA, T5, XLNet | 把输入当纯字符流（不依赖空格分词），底层用 BPE 或 Unigram。天然处理中日文等无空格语言 | 32K~100K |
| **Unigram** | T5（可选）, XLNet | 先建一个大词表，然后反复删除"对似然贡献最小"的子词，直到词表缩到目标大小 | 32K~64K |

### 3.1 BPE 工作流程（以 GPT-2 为例）

```
原始词表：单字符 {a, b, c, d, e, ...}

步骤1: 统计语料中所有相邻符号对的出现次数
步骤2: 将最高频的那对合并为一个新的子词符号
步骤3: 新符号加入词表，回到步骤1
终止: 迭代 N 次后词表达到目标大小（如 50257）

实际效果：
  "unbelievable" → ["un", "believ", "able"]   （3个子词，远小于原词长度）
  "lower"        → ["low", "er"]                （低频词被拆分，高频词保持完整）
```

> 关键洞察：BPE 会让高频词保持完整（如 "the", "a", "is"），低频词被拆成子词片段。词表大小是超参数，越大则子词越"完整"，越小则拆分越激进。

## 四、实战常见问题

**Q1：为什么加载模型时必须用同款 Tokenizer？**
不同 Tokenizer 的**词表 ID 映射完全不同**。同一个中文词"苹果"在 GPT-2 的 Tokenizer 里可能是 ID=12345，在 LLaMA 里可能是 ID=67890。用错 Tokenizer 等于在喂乱码。

**Q2：中文分词跟英文的核心区别？**
英文天然用空格分隔单词，BPE 直接在单词内部做子词拆分。中文没有空格，SentencePiece 直接把中文文本当连续字符序列处理，相当于"全字符级 BPE"，不需要预先分词。

**Q3：为什么有时一个中文词会被拆成多个 Token？**
因为这个词（或其中的字）在训练语料中出现频率不够高，BPE 没有把它合成为一个独立 Token。例如"饕餮"可能被拆成 `["饕", "餮"]` 两个单字 Token。

## 落地应用

1. **这个知识是为了解决什么问题**：分词器是文本进入模型的唯一入口。不理解特殊标记的含义，就无法正确构造模型输入、控制生成起止、处理不等长 batch 和 OOV。
2. **真实开发里会出现在哪**：NLP 后端——调用 Hugging Face `tokenizer.encode()` 时看到的 `input_ids` 里第一个和最后一个 ID；LLM API 的 `stop_sequence` 参数设计。
3. **一个最小实践 Demo**：
```python
from transformers import AutoTokenizer

tokenizer = AutoTokenizer.from_pretrained("gpt2")
# 查看特殊标记的 ID
print(f"BOS/EOS: {tokenizer.bos_token_id}, {tokenizer.eos_token_id}")  # GPT-2 共用
print(f"PAD: {tokenizer.pad_token_id}")  # GPT-2 默认无 PAD，通常设为 eos_token_id

# 编码一句文本
tokens = tokenizer("你好，世界！")
print(tokenizer.convert_ids_to_tokens(tokens["input_ids"]))
# 会看到开头没有 BOS，结尾没有 EOS——GPT-2 默认不添加！需要手动设置 add_special_tokens=True
```
4. **一个真实项目中的使用场景**：训练微调模型时，构建 DataCollator 必须指定 `pad_token_id`，否则 batch 中的不等长序列无法拼接成 tensor。对话系统的 `stop_token` 设置决定了生成何时结束——设错会导致模型无限输出。
5. **初学者最容易犯的错误**：（1）把 BERT 的 Tokenizer 用在 GPT 模型上；（2）忘了加 Attention Mask，导致 PAD 参与计算污染语义；（3）以为所有 Tokenizer 都自动加 BOS/EOS——实际上 GPT-2 的默认行为是不加。
6. **当前阶段只需要掌握到什么程度**：能说清每种特殊标记的用途和出现场景，知道 GPT 族和 BERT 族在标记体系上的核心差异，能正确调用 HuggingFace Tokenizer 完成编码/解码。
7. **学完后建议做什么练习**：分别用 GPT-2 和 BERT 的 Tokenizer 对同一段中文文本做编码，对比它们的 token IDs 序列差异（特别是开头和结尾的特殊标记）。
